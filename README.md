# yandex-positions — ночной сбор позиций Яндекса (Search API)

Единый репозиторий для всех сайтов. Полная инструкция по развёртыванию и
экономике — в файле проекта `доступы\Poziccii_Search_API.md` (рабочая папка
«Позиции»). Здесь — каркас репозитория, cron и грабли.

## Что где

```
tools/yandex-positions-<домен>/   — экземпляр сборщика на сайт:
  keywords.txt                    ключи (формат: запрос | тег)
  positions.py                    submit / collect / sync-one (ПРОПАТЧЕННЫЙ!)
  collect_parallel.py             параллельный collect (12 потоков, ~8 мин на 3к ключей)
  queue/, state/, results/        очередь разовых задач, операции по дням, срезы
.github/workflows/                workflow на сайт: <домен>-submit/-collect (+fallback'и)
```

⚠️ `positions.py` в этом репозитории — с фиксом опроса операций (`api_op`,
шлюз `operation.api.cloud.yandex.net`). Экземпляры НЕ из этого репозитория
(например, старые копии) сначала заменить на эти файлы.

## Режим работы (важно)

**Сбор — разовый, по запросу.** Все workflow'ы по умолчанию ВЫКЛЮЧЕНЫ
(disabled_manually). Регулярный мониторинг включается только по отдельному
заказу пользователя и только на его период.

Разовый срез (локально, из каталога экземпляра):

```bash
export YANDEX_SEARCH_API_KEY=... YANDEX_FOLDER_ID=... YP_REGION=<код> YP_SITE=<домен>
python positions.py submit          # окно 00:00–06:00 МСК! ~0,025 ₽/ключ
sleep 480
python collect_parallel.py          # не positions.py collect — медленно (7 ч)
git add -A && git commit -m "positions: срез <дата>" && git push
```

## Cron: когда заказан регулярный мониторинг

1. `gh workflow enable` (или API: PUT /actions/workflows/{id}/enable) для
   submit/collect пары сайта. Воркфлоу уже на collect_parallel.py — лимит
   GitHub Actions 6 ч не превышается.
2. GitHub schedule-cron задерживает запуски на 10–60 мин в час пик — для
   точного старта в 00:05 МСК подключаем внешний будильник cron-job.org
   (аккаунт obedenenie.vl@yandex.ru, см. `пригодится\cron-job.org — будильник
   ночных сборов.md`): он дёргает repository_dispatch в точное время.
3. После окончания мониторинга — ВСЁ выключить обратно (workflow disable +
   cron-job.org enabled:false).

Расписание для нескольких сайтов на одном API-ключе — со сдвигом 35 минут
(квота 1 запрос/сек на ключ; 1000 ключей ≈ 18–20 мин сабмита).

## Грабли (проверено ошибками 17–19.11, не повторять)

1. **Опрос операций только через `operation.api.cloud.yandex.net/operations/{id}`**
   (`api_op` в positions.py). Старый адрес на searchapi отдаёт 404/501:
   submit работает, деньги списываются, а результаты «недосягаемы».
2. **«collect завершён» ≠ собрано.** Проверять: записи с полем `position`/
   `inTop100`, ошибок 0–1%. Файл, полный `{"error": ...}`, блокирует пересбор
   (ключи пропускаются) — удалить `results/<дата>.json` перед повтором.
3. **Запрет массового сбора в ЛЮБОМ виде, кроме отложенного (async).**
   Используем ТОЛЬКО `searchAsync` (отложенный режим, ~0,025 ₽/ключ ночью).
   Запрещены: дневной async (всё равно 429) и **синхронный режим (`/v2/web/search`)
   даже ночью** — он стоит ~0,37 ₽/ключ (366 ₽/1000), это в ~15 раз дороже
   отложенного. Дневной синхронный — 0,49 ₽/ключ. Точечный `sync-one`
   допустим только по прямой команде пользователя (1–2 ключа для отладки),
   никогда как шаг плана. Днём — только бесплатный опрос уже отправленных
   операций (он не тарифицируется).
4. **collect однопоточный ≈ 8 с/операцию** — на 3к+ ключей это 7 ч и таймаут
   GitHub Actions. Только `collect_parallel.py`.
5. Операции живут ~12 ч: collect упал — можно дособрать днём бесплатно,
   без повторного submit.
6. Часть операций отдаёт 403 — дослать только их повторным submit'ом,
   через ~7 минут снова collect.
7. Днём async-submit гарантированно падает с 429 — это регламент окна,
   не поломка.
8. Перед первым массовым запуском на новом экземпляре — пробный прогон
   2–3 ключей полным циклом (submit → 6 мин → api_op → parse), см. раздел 10
   инструкции `Poziccii_Search_API.md`.

## Ключи и доступы

- Секрет репозитория: `YANDEX_SEARCH_API_KEY` (Search API, AI Studio).
- `YANDEX_FOLDER_ID`, `YP_REGION`, `YP_SITE` — прямо в workflow (не секреты).
- Патч/удаление workflow'ов и секретов — через API с PAT владельца
  (`доступы\`).
